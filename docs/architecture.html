飲食日誌架構

在自己電腦上執行的繁體中文飲食熱量日誌：手機拍照或打字，AI（ChatGPT 或 Claude）辨識食物與份量，熱量優先取自本機食物庫與可核對的來源，由程式計算。設計原則是準確優先，其次才是少呼叫模型。服務跑在你的電腦上，可選擇經 Tailscale serve 從自己的手機開啟。本文依目前程式碼（server/、client/、start.bat、data/）整理。

1. 系統總覽

連線與身分

  • start.bat 安裝套件、vite build、執行 tailscale serve --https=8443 --bg 3000，再 npm start。網址與帳號放在不進 git 的 start.local.bat（REMOTE_ORIGINS、OWNER_LOGIN）。
  • 伺服器只接受 Host 為 127.0.0.1:3000 或 REMOTE_ORIGINS 的請求。遠端請求沒有 Tailscale-User-Login 就拒絕。
  • 每個瀏覽器拿到 24 小時的 HttpOnly session 與 CSRF token；所有 /api 寫入都要帶 CSRF。

手機與本機限定操作

  • OWNER_LOGIN 是你的 Tailscale 登入帳號，讓手機與電腦本機使用同一本日誌 meals.sqlite。
  • 經 Tailscale 轉送的要求（帶 Tailscale-User-Login 或 X-Forwarded-*）一律視為遠端，偽造 Host: 127.0.0.1 也不算本機；開發模式拒絕所有遠端要求。
  • ChatGPT 登入、切換、登出與 AI 服務設定（/auth/*、/api/account、/api/logout、/api/providers）只能在 127.0.0.1 操作，因為 OAuth 回程網址固定在本機。

ChatGPT 登入（選用）

  • 依 OpenAI「Sign in with ChatGPT」開源 app 流程：client_id=dynamic_agent_client 動態註冊，每台機器一個隨機 ext_agent_host_id；PKCE（S256）＋OIDC（issuer、audience、nonce）驗證；回程網址 http://127.0.0.1:<PORT>/auth/callback；沒有 client secret。
  • 需要 chatgpt.tokens.use.direct scope；呼叫 Responses API 時一律 store:false、stream:true，以 SSE 串流組回結果。
  • token 到期前 30 秒自動 refresh，同一帳號同時只跑一次；invalid_grant 時清掉 token 要求重新授權；登出時嘗試撤銷 refresh token。
  • 模型清單只開放 GPT 主版本小於 6 的模型，名稱以 -sol 結尾者排第一當預設。

2. 食物辨識流程

辨識呼叫

  • 提示要求不給熱量，只給品名與可食重量；熱量交給資料庫，避免模型憑記憶給數字。
  • 常見單品料理（滷肉飯、牛肉麵）整份算一項，便當或自助餐才拆；名稱要寫出烹調方式與油量，因為這會改變比對結果。
  • 份量參照物：筷子、湯匙、手機、碗、便當盒、手搖杯，以及使用者的拳頭。拳頭寬＝身高×0.05（男）或 0.048（女），沒設計劃時用 8.5 cm；一拳容量依寬度三次方從 250 ml 換算。
  • 使用者訊息開頭附用餐時間脈絡（如「用餐時間：週三 07:40（早餐時段）」，取自工作建立時的本機時間），只作常見份量與餐點型態的參考；放在使用者訊息而非系統指示，系統指示每次相同、利於快取。AI 估算沒有用餐時間，不附。不收集地點。
  • 圖片內與使用者輸入的文字只當食物資料，不遵從其中指令。

單項查熱量

  • 本機比對用 NFKC＋去標點的正規化名稱。主名稱先比，同義名後比，因為模型給的同義名可能有誤（例如把滷蛋當茶葉蛋）。
  • 互斥詞是硬規則，連模型的 sameAs 都不能推翻：無糖↔含糖、全糖↔半糖、炸↔蒸煮烤、生↔熟、去皮↔帶皮、脫脂↔全脂。
  • 相近候選以雙字組相似度 ≥0.5 取最多 5 筆，併在查熱量那次呼叫，模型判斷相同就回 {"sameAs": id}，不多花一次呼叫。
  • web 結果只有在搜尋確實完成、且回傳網址（忽略 utm、#、結尾斜線）真的出現在工具引用中才標為網路資料；否則降為 LLM 估算並留下警告。
  • 只有每份熱量時須有每份重量才換算每 100g；無重量的每份值不採用。
  • 辨識與 LLM 估算用 API 層 JSON Schema 結構化輸出（Claude output_config.format、ChatGPT text.format strict）；web_search 那次維持自由文字 JSON，因為 Claude 在 schema 模式下不回傳引用（ADR 0007）。數值範圍仍由程式檢查。

失敗處理

  • 每次模型呼叫在同一服務上 150 秒逾時、重試 1 次；仍逾時、或遇到 400／401／403／429／5xx／網路錯誤時改用下一個 AI 服務。所有服務都失敗才中止整個工作（逾時顯示「分析逾時，請重試」）。
  • 模型回傳格式錯誤、Claude 拒絕、使用者停止都不換服務。只有搜尋本身失敗或不支援時才在同一服務改用 LLM 估算。
  • LLM 也給不出數字時中止並請使用者提供營養標示或手動填寫；不會假裝成功。
  • 伺服器重啟時 running 的工作標成錯誤；工作只留最新 20 筆。刪除執行中的工作會中止它，也不會存餐點；刪除餐點時一併刪除它已完成的工作，列出工作時也清掉對應餐點已不存在的已完成工作。
  • 自動存檔失敗時，辨識結果仍留在工作裡供重試。非中文的上游錯誤訊息一律換成通用提示，不外洩原始回應。

3. 資料庫結構

檔案來源筆數
tfda-common.json衛福部食藥署 食品營養成分資料集（2025 版 UPDATE1）137
hpa-2018-dishes.json國健署 熱量知多少（2018，中式菜餚，原頁已下架，引用封存頁；每份換算為每 100g）22

食物庫規則

  • app 內唯讀：沒有新增、修改、刪除介面。內容只來自兩條路：維護者用腳本匯入 data/*.json，以及保存餐點時自動快取未修改的 web／label 結果，和使用者在結果頁按「AI 估算」並確認保存的 LLM 結果；背景自動存檔的 LLM 估算一律不快取。
  • normalized 唯一，自動快取不覆蓋同名資料；同義名最多 20 個，靠 sameAs 與「其實是同一種」逐步學習。
  • 資料庫之後更新不會倒改既有餐點：每餐的 items 存當時的 grams 與每 100g 熱量快照。

熱量、連勝與目標

  • 每項熱量＝grams × kcalPer100g ÷ 100，四捨五入後加總，由程式計算，不由模型給。
  • 連勝 🔥：從今天往回數（今天還沒記錄就從昨天起），連續「有記錄且當日總熱量不超過目前目標」的天數。
  • settings 的 goal 介於 500～10000 kcal；fallback 決定本機查不到時先搜網路或直接估算。

減重計劃換算

BMR = 10×體重 + 6.25×身高 − 5×年齡 + (男 5 / 女 −161) TDEE = BMR × 活動係數（1.2／1.375／1.55／1.725） 下限 = max(BMR, 男 1500 / 女 1200) 每週 = (TDEE − goal) × 7 ÷ 7700 kg 天數 = ⌈(體重 − 目標) ÷ 每週 × 7⌉，從 startDate 起算

Mifflin-St Jeor 公式，前端 client/plan.js 計算；plan 也提供辨識時的拳頭大小。

4. AI 服務鏈與憑證保存

服務順序與備援

  • 設定存在 credentials.json 的 providers：預設 ChatGPT 啟用、Claude 停用；可上移／下移與個別啟用。每次呼叫只用「啟用且可用」的服務，排第一的是主要服務。
  • ChatGPT 的模型來自日誌的 settings.model；模型不在清單或取得清單失敗時略過 ChatGPT。Claude 的模型存在 provider 設定，預設 Haiku 5.5；Opus／Sonnet 啟用伺服器端拒絕備援，Haiku 用基本版 web_search。
  • 400 也會換服務，因為各家接受的要求格式不同；錯誤訊息只保留中文提示，Claude 的錯誤原文最多 200 字且遮蔽像金鑰的字串。
  • 每個品項的備註都加上實際處理的服務與模型「（由 ○○ 處理）」，不論主要或備援；已有舊標註時先移除再加，不重複。

Claude API key

  • 只能在本機設定；保存前以免費的 Token Counting API（messages.countTokens，所選模型，15 秒逾時）驗證：401／403 判為無效，未綁定工作區的金鑰回 400 並提示在工作區內建立，其他錯誤判為無法驗證，皆不保存。
  • 空字串刪除金鑰；畫面只顯示 ••••＋末四碼與加入時間。
  • Windows 換電腦或換帳號後 master.key 無法解開：服務拒絕啟動並提示刪除 credentials.json 與 master.key 後重新設定，絕不覆寫已加密的檔案。
