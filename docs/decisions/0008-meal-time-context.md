# 0008 辨識提示詞加入用餐時段

- 狀態：已採用

## 背景

辨識那次呼叫要估每一項的克數，而克數是熱量的主要誤差來源（見 [0001](0001-kcal-computed-by-program.md)）。同一種食物在不同時段的常見份量與餐點型態不同，例如早餐店的份量、宵夜的份量。

這個決定是**根據研究做的**：在提示詞加入時間、地點等情境資訊後，各模型的份量平均誤差約減少 53 g（[arXiv:2507.07048, 2025](https://arxiv.org/abs/2507.07048)）。

問題是：要加哪些情境資訊，又不影響隱私與省 token？

## 考慮過的選項

**A. 不加情境**
- 優點：提示詞最短，不必處理時間。
- 缺點：放掉研究中可降低份量誤差的資訊。

**B. 只加用餐時段（採用）**
- 優點：時間本來就有（送出分析的當下），不需收集新資料；只多一行字。
- 缺點：只有研究中情境資訊的一部分，效果可能比研究小。

**C. 時段＋位置**
- 優點：較接近研究的設定。
- 缺點：要收集位置，涉及隱私；本程式不收集位置。不採用。

## 決定

採用 B。辨識時在使用者訊息中加入一行用餐時間與時段，指令中說明時間只作參考，以照片與文字為準。

## 做法

1. **產生時段文字**：`server/food-analysis.js` 的 `mealTimeContext()` 依本機時間產生，例如「用餐時間：週三 07:40（早餐時段）」。時段劃分：
   - 05–10 早餐
   - 10–14 午餐
   - 14–17 下午點心
   - 17–21 晚餐
   - 21–05 宵夜
2. **傳入時間**：`analyzeMeal()` 多一個參數 `at`；`server/food-routes.js` 在背景分析時傳入該分析工作的建立時間（也就是送出當下，與自動存檔的餐點時間相同）。
3. **放在使用者訊息，不放在指令**：時間那一行放在 `input` 的使用者內容最前面；系統指令（`instructions`）每次都相同，有利於供應商的提示詞快取。
4. **指令中只多一句**：「用餐時間只作為判斷常見份量與餐點型態的參考……以照片與文字為準，不要因時間改變看得到的內容。」這句不論有沒有傳時間都在，所以指令文字不變。
5. **「AI 估算」不送時間**：結果頁單項「AI 估算」（`/api/estimate`）呼叫 `analyzeMeal()` 時不帶 `at`，因為它可能用在較早之前的餐點，現在的時間不代表那餐的時間。

## 取捨

- 約 53 g 的效果是在另一個資料集、包含時間與地點的設定下測得，本程式只加時段，實際效果未知。
- 每次辨識多幾個 token（一行時間文字），指令不變，不影響快取。
- 半夜補記前一餐時，時段會不準；指令已要求以照片與文字為準。

## 何時重新評估

- 用自己記錄的餐點（有修正過克數的項目）比較加與不加時段的克數誤差；若沒有改善，可拿掉。
- 若之後支援補記過去時間的餐點並送分析，改傳那餐的時間而不是送出時間。
