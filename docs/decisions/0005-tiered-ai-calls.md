# 0005 省 token 的分層呼叫設計

- 狀態：已採用

## 背景

算一餐熱量要三步：認出食物與克數 → 找每 100g 熱量 → 相乘。每呼叫一次 AI 都要花 token、時間與額度。若每一步、每一樣食物都交給 AI，一餐 4 樣就可能 8 次以上呼叫；而 AI 憑記憶給的熱量，事後無法核對。

原則：**準確優先，其次省 token；兩者衝突時，選準確。**

## 考慮過的選項

**A. 一次大呼叫全包**（食物、克數、熱量一次回傳）
- 優點：呼叫最少，每餐 1 次。
- 缺點：熱量來自模型記憶，沒有來源、無法核對，違反準確優先（見 [0001](0001-kcal-computed-by-program.md)）。

**B. 每樣食物各自呼叫**（分別辨識、分別查熱量）
- 優點：程式最簡單。
- 缺點：呼叫數隨食物數倍增；吃過的食物也要重新問。

**C. 分層查詢（採用）**：程式先查，答不出來才呼叫 AI；能併的呼叫就併。
- 優點：熟悉的餐只要 1 次；熱量盡量有可核對的來源。
- 缺點：程式路徑較多，各自都要測。

## 決定

採用 C：**AI 只在程式答不出來時才呼叫；非叫不可時，一次把能併的事情做完。**

| 層 | 做什麼 | AI 呼叫 |
| --- | --- | --- |
| ① 辨識＋讀營養標示 | 所有食物一起辨識 | 每餐 1 次 |
| ② 本機食物庫 | 名稱／別名完全比對 | 0 次，命中就停 |
| ③ 網路搜尋＋比對相近候選 | 同一次呼叫裡先判斷「是否同一種」，不同才搜尋 | 每樣未收錄食物 1 次 |
| ④ LLM 估算 | 搜不到可核對資料才估 | 再 1 次 |

營養標示可讀的品項在 ① 就有熱量；③ 若判斷和本機某項是同一種，直接用本機資料，不再搜尋。

## 做法

1. **一餐只辨識 1 次**：`server/food-analysis.js` 的 `analyzeMeal()` 一次回傳所有食物（最多 15 項）。照片先在手機上由 `client/App.jsx` 的 `compressPhoto()` 縮成長邊 1280 px、JPEG 品質 0.82 再上傳，圖片 token 也省。
2. **營養標示在同一次讀，額外 0 次**：標示清楚時辨識結果直接附 `labelKcalPer100g`，記為「營養標示」來源，不再查。
3. **本機食物庫完全命中，0 次**：`localItem()` 呼叫 `server/journal.js` 的 `findFood()`，命中就用庫內熱量。
4. **相近候選併進同一次搜尋**：`lookupItem()` 以 `candidates()` 取最多 5 筆候選，只送 `id`／`name`／`aliases`，不送整個食物庫。有候選時 `tool_choice` 為 `auto`（判斷相同就不必搜尋），沒有候選則為 `required`。
5. **查不到可核對資料，才 LLM 估算**：網址要通過 [0002](0002-citation-verification.md) 的引用核對才算網路來源。估算時若搜尋那次已比對過候選，就不再重複送候選（`askCompare`）。設定為「直接由 LLM 估算」時跳過搜尋，候選改在估算那次一起判斷。
6. **未收錄的食物最多 3 項同時查**：`analyzeMeal()` 以 3 個 worker 並行，結果放回原本位置。這是為了速度，不是為了省 token。
7. **逾時只重試 1 次，特定錯誤才換服務**：`server/food-routes.js` 的 `retryOnTimeout()` 每次呼叫預設 150 秒逾時，只在逾時時重試 1 次；`fallbackWorthy()` 只在 400／401／403／429／5xx、逾時、網路錯誤時換下一個 AI 服務；回傳格式錯誤、拒絕、使用者中止不換——避免重試風暴。（Claude 的 SDK 用戶端另設 `maxRetries: 1`。）
8. **衝突時準確勝出**：搜尋比直接估算多花 token，仍先找可核對資料（優先食藥署食品營養成分資料庫）。

## 實例：4 樣的雞腿便當（示意）

| 食物 | 走到哪一層 | AI 呼叫 |
| --- | --- | --- |
| （整餐） | 辨識，4 樣一次 | 1 |
| 白飯 | 本機食物庫命中 | 0 |
| 滷蛋 | 本機食物庫命中 | 0 |
| 炸雞腿 | 網路搜尋找到，引用核對通過 | 1 |
| 燙青菜 | 搜尋無可核對資料 → LLM 估算 | 1 + 1 |
| **合計** | | **4 次** |

再吃一次熟悉的餐（每樣都已在本機庫）→ 只有辨識 **1 次**。

網路查到的炸雞腿會存進食物庫；LLM 估算的燙青菜要使用者確認後才入庫（見 [0004](0004-food-library-caching.md)）。

## 取捨

- 每樣沒見過的食物多 1～2 次呼叫；搜尋比直接估算貴，換來可核對的來源。
- 程式分支變多：標示、本機、候選、搜尋、估算都要各自測試。
- 3 項並行只加快速度，不省 token。

## 何時重新評估

- 模型呼叫變得很便宜，或 AI 能附可驗證的來源。
- 本機庫命中率一直很低。
- 一餐常超過 15 項，或並行時常被限流。
- 搜尋常落空，大多落到 LLM 估算。
