# 0004 快取策略：什麼可以存進本機食物庫

- 狀態：已採用

## 背景

分析每一餐時，本機食物庫（SQLite `foods` 表）找不到的食物，要上網查或請 LLM 估算：每項 1 次以上 AI 呼叫，要等、要花 token。把結果存起來，下次同名食物就直接命中、0 次 AI 呼叫——「越用越快、越用越省」。

但命中的資料會標成「本機庫」直接沿用、不再查證。存進一筆錯的，之後每一餐都跟著錯，而且看起來很權威。要決定的是：哪些結果夠可信、可以自動存？誰的確認算數？已經存的資料可以被蓋掉嗎？

## 考慮過的選項

**A. 全部都存**
- 優點：學得最快，第二次起幾乎都命中；最省 token。
- 缺點：估錯一次就永久錯；之後顯示「本機庫」，像是查證過；錯誤會累積且不易察覺。

**B. 完全不存，每次都查**
- 優點：不會累積錯誤；每次成本一致。
- 缺點：不會學習，同一道菜每次都花 token、都要等；同一食物每次數字略有不同。

**C. 只存可查證的；估算要使用者點頭（採用）**
- 優點：常吃的食物越來越快、越省；庫裡每筆都有出處或經使用者確認。
- 缺點：部分其實正確的估算每次重估；第一筆存進去就算數。

## 決定

採用 C：

1. **自動寫入只限可查證的來源**：網路資料（網址通過 [0002](0002-citation-verification.md) 的引用核對）與照片中清楚可讀的包裝營養標示。
2. **LLM 估算要使用者點頭**：背景分析自動存檔時一律不寫入；只有使用者在結果頁按「AI 估算」、看過後按保存，才寫入。
3. **先來的不被覆蓋**：名稱正規化後已在庫裡，就保留舊資料，新結果只記在這一餐。
4. **改過的不存**：使用者手動改了名稱或每 100g 熱量，這項就不寫入；只改克數不影響。
5. **學別名，不學數字**：判斷為「同一種」時，只把這次辨識的名稱記成既有食物的別名，下次直接命中，不改既有數字。
6. **每餐存快照**：餐點存的是當下的完整數字；食物庫之後變動，不會改寫歷史紀錄。

## 做法

寫入點在 `server/journal.js` 的 `saveMeal()`，三個條件都成立才呼叫 `putFood(item, false)`（`false` = 不覆蓋）：

1. `item.cache` 為 true——由產生結果的程式決定。
2. 不是本機庫命中（`!item.matched`）。
3. 來源屬於 `AUTOMATED`（`web`、`llm`、`label`）。

`llm` 在 `AUTOMATED` 裡，所以估算能不能存，全看 `cache` 旗標：

| 來源 | 情境 | 寫入食物庫？ | 程式位置 |
| --- | --- | --- | --- |
| 網路資料 | 引用核對通過 | 寫入 | `server/food-analysis.js` 的 `lookupItem()` 設 `cache: true` |
| 網路搜尋 | 網址不在引用裡 → 降級為 LLM 估算 | 不寫入 | 同上，降級後依 LLM 估算規則 |
| 包裝營養標示 | 照片中標示清楚可讀 | 寫入 | `analyzeMeal()` 設 `cache: true` |
| LLM 估算 | 背景分析自動存檔 | 不寫入 | `server/food-routes.js` 的 `/api/analyze` 把 `llm` 項目改成 `cache: false` |
| LLM 估算 | 已存餐點的「重新查詢」 | 不寫入 | `/api/jobs/relookup` 同樣改成 `cache: false` |
| LLM 估算 | 使用者按「AI 估算」→ 看過後保存 | 寫入 | `/api/estimate` 保留 `cache: true`，`client/App.jsx` 的 `estimate()` 放回草稿 |
| 本機庫命中 | 直接命中，或模型判斷「同一種」 | 不重寫 | `localItem()`、`lookupItem()` 設 `matched: true` |
| 任何來源 | 使用者改了名稱或每 100g 熱量 | 不寫入 | `client/App.jsx` 編輯時改為 `source: 'manual'`、`cache: false` |
| 任何來源 | 只改克數 | 照原規則 | 不動 `cache` |
| 手動新增 | 使用者自己填的熱量 | 不寫入 | `addManual()`：`source: 'manual'` |
| 任何自動來源 | 同名（正規化後）已在庫裡 | 不覆蓋 | `putFood(item, false)` |
| 判斷為同一種 | 模型 `sameAs` 命中，或使用者按「其實是同一種」 | 只加別名 | `saveMeal()` 呼叫 `addAliases()` |

- **別名**：項目為 `matched` 且帶有 `recognizedName` 時，`saveMeal()` 呼叫 `addAliases()`，把辨識名稱加為別名（每筆最多 20 個）。來源有兩種：模型在 `lookupItem()` 判斷 `sameAs`，或使用者在結果頁按「其實是同一種」（`useSame()`）。使用者按「不是這個」（`notSame()`）會清掉這個對應。
- **快照**：`meals.items` 存整份 JSON（含 `kcalPer100g`），一餐熱量讀取時由快照計算，食物庫之後改動不會回頭改歷史。
- **app 內不能修改食物庫**：`putFood()` 只在保存餐點時呼叫；修正與匯入由維護者用腳本處理（`npm run import-foods`）。
- 設定頁也告訴使用者：「網路資料與營養標示會自動存入食物庫；LLM 估算不會自動存入」。

## 取捨

- **多花一些 token**：部分其實正確的 LLM 估算不會存，下次又估一次，數字也會小幅浮動。
- **第一筆為準**：最早存進的網路資料若有誤，之後更好的結果也蓋不掉。
- **app 內不能改／刪食物庫**（刻意的）：避免隨手改壞，修正要用腳本。
- **核對網址 ≠ 保證正確**：只證明來源真的被查到，不保證數字或品項完全相符。
- **模型判斷的「同一種」會在背景存檔時加為別名**：結果頁會顯示「判斷與本機庫相同」並提供「不是這個」，但若使用者沒有檢查，別名已經寫入。

## 何時重新評估

- 同一估算食物反覆出現、浮動明顯或 token 成本變高 → 考慮「多次估算一致才存」。
- 快取錯誤開始影響紀錄 → 加修正流程，例如命中時數字差很多就提示比對。
- 搜尋工具的引用格式改變、核對失效 → 先停用網路資料自動寫入，改為需確認。
- 模型 `sameAs` 誤加別名的情況變多 → 改成使用者確認後才加別名。
