# 0003 互斥詞硬規則

- 狀態：已採用

## 背景

每項食物會先到本機食物庫找「同一種」，找不到才上網查或估算。但名字相近的常常不是同一種：無糖綠茶與全糖綠茶、炸雞腿與烤雞腿、去皮雞胸與帶皮雞胸。一旦誤判成同一種，就會沿用錯的每 100g 熱量，而且之後每次都命中同一筆，錯誤反覆出現。

模型通常判斷得對，但偶爾會合併相似品項，事後也很難驗證。問題是：哪些差異必須由程式保證？

## 考慮過的選項

**A. 只靠模型判斷**
- 優點：不用維護清單；能理解各種寫法與同義名稱。
- 缺點：偶爾把相似品項合併；無法事前驗證；同樣輸入每次判斷可能不同。

**B. 向量／語意相似度**
- 優點：自動，不用手寫清單；能抓到寫法不同的同義名稱。
- 缺點：在這裡反而更糟——「炸雞腿」和「烤雞腿」語意很近，但正是要分開的東西；還要多維護一套嵌入模型與索引。

**C. 小清單硬規則＋模型（採用）**
- 優點：影響熱量最大的差異一定擋下；規則看得懂、可測試、0 token。
- 缺點：清單手動維護、不完整；子字串比對可能誤觸發；其餘細節仍靠模型。

## 決定

採用 C，兩層把關：

- **軟層（提示詞）**：幫模型判斷得更準，但不保證。
- **硬層（程式）**：最終決定，模型無法推翻。互斥的食物在算相似度之前就被剔除，模型根本看不到這些候選。

## 做法

**硬層：`server/journal.js`**

- `EXCLUSIVE`：6 組互斥詞。同一組裡，一邊名稱含左側詞、另一邊含右側詞，就一定不是同一種：

  | 左側 | 右側 |
  | --- | --- |
  | 無糖、零糖、0糖、不加糖、無加糖、零卡 | 有糖、含糖、加糖、全糖、半糖、微糖、少糖、減糖 |
  | 全糖 | 半糖、微糖、少糖、減糖 |
  | 炸 | 水煮、清蒸、蒸、烤、滷、燙、涼拌 |
  | 生食、生的、未煮 | 熟、煮、蒸、烤、炸、滷、燙 |
  | 去皮 | 帶皮、連皮 |
  | 脫脂、低脂 | 全脂 |

- `conflicts(a, b)`：兩邊先 `normalize()`，各自判斷落在左側或右側，**左側優先**——「不加糖」含「加糖」、「未煮」含「煮」，先比左側，所以仍歸左側。
- `findFood(names)`：完全比對前先剔除互斥項目（同義名稱可能較籠統，所以完全命中也要先過檢查）；再依序比對，主名稱優先於模型給的同義名稱。
- `candidates(names)`：先剔除互斥項目，再算字元雙字組（Dice）相似度，留下 ≥ 0.5 的前 5 筆交給模型判斷。

**軟層：`server/food-analysis.js`**

- `analyzeMeal()` 的辨識指令：名稱要寫出看得到的烹調方式與油量；同義名稱不能把不同做法視為同義（如茶葉蛋≠滷蛋≠水煮蛋）。
- `lookupItem()` 的比對指令：品牌、口味、有糖／無糖、生熟、烹調方式、部位都必須相同才算同一種；不確定就當作不同。搜尋時也要求和品項及烹調狀態相符。
- 模型回的 `sameAs` 只能是候選清單內的 id，其他值一律無效。

## 取捨

- **清單手寫、不完整**：例如茶葉蛋與滷蛋只靠提示詞與「主名稱優先」補強，不在 `EXCLUSIVE` 裡。
- **子字串會誤觸發**：「炸醬麵」的「炸」不是油炸，「熟成牛排」含「熟」。後果是錯過命中、多查一次（多花 token），但不會算錯熱量——準確優先。
- **只認字面**：「左側優先」只解決「不加糖」「未煮」這類包含關係，其他否定寫法要另外加詞。
- 可自行調整：編輯 `server/journal.js` 的 `EXCLUSIVE`。

## 何時重新評估

- 烤的品項吃到炸的熱量、有糖／無糖混用 → 在 `EXCLUSIVE` 加一組互斥詞。
- 明明同一種卻一直被擋、重複上網查 → 收窄詞或加例外（如「炸醬」不算「炸」）。
- 食物庫變大、名稱寫法變雜，清單跟不上 → 改用結構化欄位（烹調方式、含糖量）比對。
- 換更強的模型後：硬層仍保留（0 token、結果可預期），只是不必再擴充。
